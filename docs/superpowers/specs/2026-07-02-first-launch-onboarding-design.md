# 首次安装核心能力预览页设计

## 背景

当前应用首次安装启动后会直接进入首页，缺少一个轻量的产品介绍入口。对于新用户来说，首页已经包含数据归家、数字分身、任务执行等能力，但缺少从“为什么使用这个 App”到“进入首页开始使用”的过渡。

本设计目标是在首次安装后展示 3 页核心能力预览，引导用户理解产品主线：从各类 App 数据汇总，到个人数字分身助手生成，再到 Agent 执行个性化任务。用户点击“开始使用”后进入首页，以后不再自动出现。

## 目标

- 首次安装或清空本地完成标记后，启动展示 3 页产品能力预览。
- 三页主题固定为“数据归家 / 数字分身 / 自动执行”。
- 用户在第 3 页点击“开始使用”后进入首页，并写入完成状态。
- 完成后再次启动 App 不再出现引导页。
- 引导页视觉风格与现有首页、设置页保持统一，使用浅色背景、蓝紫强调色和清晰的信息层级。
- 不改变现有首页、底部 Tab、模型配置、设置页、Agent 执行链路。

## 非目标

- 不做权限申请、账号登录、模型下载或 API Key 配置。
- 不把引导页做成可反复进入的功能页面。
- 不在引导页里调用云端服务或读取用户业务数据。
- 不迁移已有配置存储 key。
- 不在 `Index.ets` 中堆叠复杂 UI 和页面内部状态。

## 已确认方案

采用 `Index` 内部全屏引导组件方案：

- `Index.ets` 读取持久化完成状态。
- 未完成时渲染 `FirstLaunchOnboarding`，隐藏底部 Tab 和首页内容。
- 完成后恢复现有 Tab 主页结构，默认进入首页。
- `Index.aboutToAppear()` 中已有服务初始化继续运行，引导页只作为 UI gate。

该方案比新增独立路由更轻量，也避免引导页进入路由栈后带来的返回行为歧义；同时保持 `Index.ets` 的职责为顶层编排，具体 UI 拆到独立 onboarding 模块。

## 页面结构

新增组件放在：

- `entry/src/main/ets/pages/onboarding/FirstLaunchOnboarding.ets`
- `entry/src/main/ets/pages/onboarding/OnboardingTypes.ets`

`FirstLaunchOnboarding` 负责展示和交互：

- 内部维护当前页索引。
- 支持左右滑动切换。
- 前两页主按钮为“下一页”。
- 第三页主按钮为“开始使用”。
- 点击“开始使用”后调用 `onComplete()`。

`OnboardingTypes` 负责沉淀稳定数据：

- 当前引导版本常量。
- 持久化 key 常量。
- 三页标题、副标题、说明和资源名。
- 判断是否应展示引导页的纯函数，便于单元测试。

## 持久化状态

使用版本化完成标记，而不是简单 boolean。

使用 key：

```text
firstLaunchOnboardingVersion
```

当前版本值：

```text
2026-07-core-preview
```

展示规则：

- 存储值不等于当前版本时，展示引导页。
- 用户点击“开始使用”后，将存储值写为当前版本。
- 系统返回、关闭 App、异常退出都不写完成状态。

版本化设计满足“以后不再出现”的当前要求，同时保留未来产品需要重新展示新版引导时的扩展能力。

## 三页内容

### 数据归家

表达重点：各类 App 数据被归集到个人数据中心，形成可检索、可总结、可被助手使用的个人上下文。

建议文案：

- 标题：数据归家
- 说明：汇总聊天、图库、任务和位置线索，让分散在各个 App 里的信息回到你的个人数据中心。

主视觉：多个 App 数据卡片、图片缩略图、消息气泡和位置标记流向一个带隐私盾牌的个人数据中心。

### 数字分身

表达重点：基于个人数据与头像生成个人数字分身助手，能够理解用户偏好和长期上下文。

建议文案：

- 标题：数字分身
- 说明：结合个人资料、头像和历史上下文，生成更懂你的助手，用于问答、陪伴和任务协作。

主视觉：温暖的数字人头像、聊天气泡、语音波形和个人画像卡片，体现助手与用户的关系。

### 自动执行

表达重点：Agent 可以规划步骤、等待确认并执行个性化任务，强调自动化能力和安全边界。

建议文案：

- 标题：自动执行
- 说明：让 Agent 根据你的目标规划步骤、调用工具并执行任务，关键动作保留确认边界。

主视觉：手机任务流、步骤清单、确认按钮、执行轨迹和工具节点，展示从计划到执行的闭环。

## 视觉资产策略

使用 `imagegen` 生成 3 张统一风格主视觉图，但不把整页 UI 做成一张图片。

原因：

- 生成图中文字稳定性不足，不适合承载中文标题、说明和按钮。
- ArkUI 原生文本更清晰，便于响应式布局和无障碍。
- 图片只承担情绪和功能表达，页面结构由代码控制，更易维护。

实施约束：

- 三张图不包含关键中文文字，最多包含抽象符号。
- 统一浅色背景、蓝紫强调色、柔和 3D 或玻璃质感。
- 图片资源放在 `entry/src/main/resources/base/media`。
- 资源名：
  - `onboarding_data_home.png`
  - `onboarding_avatar.png`
  - `onboarding_agent.png`

如果图片加载失败，组件展示同色系兜底图形区域，不阻塞用户继续使用。

## 交互规则

- 第 1 页和第 2 页不提供显眼跳过入口，只展示“下一页”。
- 第 3 页展示“开始使用”。
- 可左右滑动切换页面。
- 底部展示进度点，标识当前位置。
- 进度点不作为强入口，避免用户快速跳过理解链路。
- 引导期间底部 Tab 不显示。
- 点击“开始使用”后进入首页，设置 `MainTabIndex.Home`。

## Index 集成边界

`Index.ets` 只做顶层判断和状态写入：

- 通过 `PersistentStorage.persistProp` 初始化 `firstLaunchOnboardingVersion`，再用 `@StorageLink` 读取和写入当前值。
- 根据版本判断是否展示 `FirstLaunchOnboarding`。
- 处理 `onComplete()`：写入版本、切回首页。

不在 `Index.ets` 中实现：

- 三页具体 UI。
- 图片兜底布局。
- 当前页索引和滑动状态。
- 文案数组和资源映射。

这样可以继续遵守项目约定：`Index.ets` 只承担页面级编排，不承载具体业务 UI。

## 容错与边界

- 引导页不发起网络请求，因此不会受 API Key、模型服务或权限状态影响。
- 引导页不触发权限弹窗，避免首次启动流程被系统弹窗打断。
- 系统返回或关闭 App 不写完成状态，下次启动继续展示。
- 若持久化读取失败，按未完成处理，优先保证用户能看到引导并进入首页。
- 若图片资源缺失或解码失败，显示兜底视觉，不影响“下一页”和“开始使用”。

## 验收标准

- 首次安装或清空 `firstLaunchOnboardingVersion` 后，启动展示引导页。
- 第 1 页、第 2 页点击“下一页”进入下一页。
- 第 3 页点击“开始使用”进入首页。
- 完成后重启 App 不再展示引导页。
- 引导期间底部 Tab 不显示，完成后底部 Tab 正常展示。
- 三页分别清晰表达“数据归家 / 数字分身 / 自动执行”。
- 1080 x 2340 手机预览下无文字遮挡、按钮溢出、图片非等比拉伸。
- 现有首页、汇总、聊天、任务、设置页面入口不受影响。

## 验证计划

- 静态检查：`git diff --check`。
- 单元测试：覆盖版本判断、完成状态判断、三页数据顺序和按钮状态。
- Hvigor 测试：运行 entry 模块测试，确认 ArkTS 编译与现有测试通过。
- UI smoke：
  - 清空完成标记后启动 App，确认展示引导页。
  - 滑动和按钮翻页均可用。
  - 第 3 页点击“开始使用”后进入首页。
  - 重启后直接进入首页。
  - 验证底部 Tab 在引导期间隐藏、完成后恢复。

## 风险

- 生成图片若包含不可控文字，可能影响观感。规避方式是生成时明确要求无文字，关键文案全部由 ArkUI 渲染。
- 如果 `Index.ets` 条件渲染处理不当，可能影响现有初始化或底部 Tab 状态。规避方式是只把引导页作为 UI gate，保留 `aboutToAppear()` 既有初始化。
- 如果持久化 key 命名不稳定，后续版本管理会混乱。规避方式是集中在 `OnboardingTypes.ets` 导出 key 和版本常量。
